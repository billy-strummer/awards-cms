## 3. Policies dropped and created, by migration

- **045** (`proper-rls-policies.sql`): drops and replaces permissive policies on ~45 tables including `award_years`, `organisations`, `entries`, `winners`, `votes`, `events`, `invoices`, `payments`, `activity_logs`, `email_templates`, the 6 CRM tables, `sponsorship_opportunities`, and a generic "remaining tables" array of ~30 more (including `award_assignments`, `organisation_contacts`, `notifications`, `tenant_branding`, `org_activity_notes`). Creates `<table>_service` (service_role, ALL) and `<table>_select` (authenticated, SELECT) pairs, with a few table-specific extras (`entries_insert`/`entries_update` scoped to `contact_email = user_email()`, `entries_anon_select` for published entries, `votes_anon_insert`). **Never confirmed applied anywhere.**
- **052** (`rls-policies.sql`): creates `service_role_all` + `no_direct_client_access` on `organisations`, `award_years`, `entries`, `award_assignments`, `event_guests`, `invoices`, `payments`. **Does not drop any pre-existing policy** — this is the root defect BTA-079 identified. **Never confirmed applied anywhere.**
- **078** (`remove-obsolete-permissive-policy-event-guests.sql`): drops only `"Allow all access to event_guests"`. Single-purpose, correctly scoped. **Never confirmed applied anywhere** (its own empirical anon-key test, cited in its header comment, was almost certainly run against the test project, not production — see Section 5).
- **079** (`restore-event-guests-checkin-access.sql`): creates `event_guests_select`/`event_guests_update` (authenticated, SELECT/UPDATE only), matching `check-in-app.js`'s exact real usage. **Never confirmed applied anywhere.**
- **087** (`harden-sponsorship-opportunities-rls.sql`): drops `"Allow all access to sponsorship_opportunities"`, `"sponsorship_opportunities_service"`, `"sponsorship_opportunities_auth"` (045's own names for this table), creates `service_role_all`/`no_direct_client_access`, revokes all anon/authenticated grants. **Never confirmed applied anywhere.**
- **088** (`harden-remaining-046-grant-array-tables.sql`): drops every exact live-observed policy name across its 22 tables (including the leftover permissive policies and the ineffective newer `anon`-read/`authenticated`-full pairs), creates `service_role_all`/`no_direct_client_access`, revokes all anon/authenticated grants. **Never confirmed applied anywhere.**
- **093** (`harden-remaining-permissive-policy-tables.sql`): drops the original permissive policy plus defensively every one of 045's policy-name variants, for `organisations`/`organisation_contacts`/`entries`/`award_assignments`/`invoices`/`payments`/`award_years`; drops `gdpr_requests`'s 3 live-observed policies by exact name. Creates `service_role_all`/`no_direct_client_access`, revokes all anon/authenticated grants. **Explicitly excludes `event_guests`.** **Not applied; not yet tested against any database (test-project connectivity blocked since BTA-081).**

## 4. Grants vs. revokes comparison

045's generic loop only revokes `INSERT, UPDATE, DELETE` from `anon` — it does not revoke `SELECT`, relying instead on RLS's default-deny-when-no-matching-policy behaviour to block anon reads. 052/087/088/093 all additionally use the stronger, more defensive pattern of `REVOKE ALL ON public.<table> FROM anon` and `FROM authenticated` — an explicit belt-and-suspenders layer independent of the RLS policy layer. This is a genuine design improvement in the newer migrations over 045, not merely a style difference: if a future migration or manual dashboard change ever re-introduces a permissive policy, the `REVOKE ALL` grants in 087/088/093 would still block `anon`/`authenticated` at the privilege layer, whereas 045's narrower revoke would not block `SELECT`.

## 5. Permissive-policy OR behaviour — why this matters for every migration here

PostgreSQL combines multiple `PERMISSIVE` policies on the same table/command with logical OR. A `PERMISSIVE` policy with `USING (true)` therefore defeats any other `PERMISSIVE` policy on the same role/command, including `USING (false)`, because `true OR false = true`. This is the exact mechanism behind every exposure found in BTA-078/079 and the reason 052 (as written) would not have worked even if applied: it adds a `USING (false)` policy alongside the original `USING (true)` policy without dropping the latter. 087/088/093/078 all correctly avoid this by dropping the original policy's exact name before adding anything new — confirmed by direct re-read of all four files this task. No `RESTRICTIVE` policy is used anywhere in this migration set; everything relies on dropping conflicting `PERMISSIVE` policies rather than layering a `RESTRICTIVE` one on top, which is consistent with the simpler mental model (one clear PERMISSIVE policy per role, no original left behind) and is not itself a defect.

## 6. Overlapping or conflicting migrations

- **045 vs. 052**: conflicting intended end-states (045: `authenticated` can read; 052: nobody but `service_role` can do anything) for `organisations`, `award_years`, `entries`, `award_assignments`, `invoices`, `payments`. **Resolved in practice by 093**, which supersedes 052's intent for these 6 tables (full lockdown) based on BTA-080's confirmed-zero-dependency evidence, and defensively drops 045's policy names too so the conflict cannot resurface even if 045 is ever separately applied.
- **087 vs. 045**: 087 correctly drops 045's `sponsorship_opportunities_service`/`sponsorship_opportunities_auth` names — no residual conflict.
- **093 vs. 052**: 093 is not a drop-in replacement for the 052 *file* (093 has its own filename/header and additionally covers `organisation_contacts`/`gdpr_requests`, which 052 never touched), but it fully supersedes 052's *intent* for the 6 tables they share. **052 should not be applied on its own** — if it were applied before 093, its own-named `service_role_all`/`no_direct_client_access` policies would simply be redundant with (not contradicted by) 093's later identically-named policies on the same tables, since `CREATE POLICY` with the same name twice is idempotent-safe under `duplicate_object` handling in 093 — but 052 still would not have dropped the *original* policy, so applying 052 alone remains pointless either way.
- **078/079 vs. 052**: 052's array includes `event_guests` with its own `service_role_all`/`no_direct_client_access` — if 052 were ever applied after 078+079, this is harmless (PERMISSIVE policies only add access via OR, so a `USING (false)` policy can't subtract what `event_guests_select`/`event_guests_update` already grant to `authenticated`), but 093 deliberately takes no position on 052's fate and does not depend on this reasoning.

## 8. `event_guests` exception — confirmed, re-read this task

`check-in-app.js` (the deployed Event Check-in staff tool, served from `check-in.html`) makes direct, `anon`-key-initialized Supabase client calls, scoped to the `authenticated` role at the policy level: `SELECT` to load the guest list (`loadGuests()`) and look up a scanned QR code, `UPDATE` to mark `checked_in`/`check_in_time` (`performCheckIn()`/`checkInByButton()`). No `INSERT`, no `DELETE`. Migration 079's two policies (`event_guests_select`, `event_guests_update`) match this exactly — confirmed by direct re-read of both the migration file and `check-in-app.js` this task (unchanged from BTA-080's findings). Migration 093's own header comment explicitly documents why it excludes this table, and a direct grep of 093's source (performed in BTA-080, via `tests/migration-093.test.js`) confirms no statement in 093 references `event_guests` at all.

## 9. Conceptual migration-order assessment

All 7 migrations in this reconciliation are mutually independent at the SQL object level (confirmed: none of them `CREATE`/`ALTER`/`DROP` an object another one also touches, except where one migration's own `DROP POLICY IF EXISTS` targets a policy name another migration later also drops defensively — which is idempotent and harmless). A reasonable application grouping, once the test project is reachable: **093 → 087 → 088** as one batch (closes the permissive-policy exposure across all 31 of the 32 tables not already handled by 078/079), with **078 → 079** as a second, already-complete batch for `event_guests` specifically (if not already applied — unconfirmed). **052 and 045 should not be applied at all** going forward — 093 supersedes 052's relevant intent, and 045's broader scope (many tables outside this 32-table set, e.g. `winners`, `votes`, `events`, CRM tables) was not re-examined in this reconciliation and is a separate question for a future task if those tables are ever found newly exposed.

## 11. CORRECTION (added after this report's initial writing, same task) — migration 093's "zero dependency" premise is wrong

**BTA-085 (run in parallel within this same BTA-084–093 programme) found that migration 093's own header comment, and BTA-080's compatibility analysis it was based on, used a single-line grep pattern (`supabase\.(from|rpc)\(`) that misses this codebase's common multi-line method-chain style (`supabase\n  .from(...)`).** A corrected, multiline-aware search found a real, deployed admin feature — `test-data-manager.js`, loaded into every admin session via `src/partials/99-shell-foot.html` — that directly reads/writes **34 tables** via a browser-side `STATE.client` (the `authenticated`-role Supabase client), including **every one of migration 093's 8 target tables except `gdpr_requests`**, plus `event_guests` (the table 093 deliberately excludes, on the assumption 078/079 already cover it — but `test-data-manager.js` needs INSERT/DELETE there, which 078/079's SELECT/UPDATE-only policies do not grant).

This does not mean migration 093 is wrong to lock these tables down — `test-data-manager.js`'s own header comment confirms this bypass is a **deliberate, documented architectural exception** ("STATE.client.from() is intentional: test data setup requires direct DB access... that bypasses RLS and validation for test fixture management"), not a legitimate production workflow. But it does mean **093 would break this admin tool if applied as-is**, and Section 9/10 of this report's "explicit conditions before production deployment" must be read as incomplete without this correction: a decision is needed (refactor `test-data-manager.js` to go through `api/data-proxy.js`; carve out scoped `authenticated` policies for it; or accept it breaking and gate the feature off) before 093 is applied anywhere, including the test project. **This is a business/architecture decision, not resolved here.** See `BTA-085-APPLICATION-SECURITY-DEPENDENCIES.md` Section 8.1 for full evidence, and `BTA-093-CONSOLIDATED-IMPLEMENTATION-ROADMAP.md` for how this is carried into the prioritised plan.
