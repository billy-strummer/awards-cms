# BTA-089 — Administrative Interface Audit

**Date:** 2026-11-02
**Type:** Read-only investigation. No application code, permissions, or configuration was modified. No Supabase connection was made.

## Executive summary

The admin interface is large (dashboard, organisations, entries, awards, assignments, settings, areas, marketing/sponsorship, GDPR — ~28,000 lines across the modules reviewed) and consistently follows the `ModuleRegistry` + `apiClient` + `data-action` click-delegation pattern — no module was found using a legacy `onclick="..."` pattern instead. However, three **Confirmed** permission/UI-consistency defects were found, all stemming from the client-side RBAC layer (`rbac.js`) not having been kept in step with later changes elsewhere in the codebase. None of these are live data-exposure risks on their own — the server-side `ROLE_PERMISSIONS`/`ALLOWED_RPCS` gates in `api/data-proxy.js` still correctly block unauthorized writes — but they are real usability/consistency defects that would surface as confusing behaviour or unnecessary admin friction.

## Findings by module

### `rbac.js` — the permission model itself

- **Confirmed (Medium): the `data-rbac-action` attribute-based UI-hiding mechanism `rbacModule.applyPermissions()` provides (rbac.js:180–183) is unused anywhere in the codebase.** A repository-wide check across `organisations.js`, `entries.js`, `awards.js`, `assignments.js`, `settings.js`, `marketing.js`, `dashboard.js`, `gdpr.js` found zero occurrences of `data-rbac-action`. The only client-side permission enforcement actually operating today is: (a) whole-tab show/hide via the hardcoded `tabMap` (module-level only, e.g. hiding the entire Payments tab from non-finance roles), (b) a selector-based disable of delete buttons (see next finding), (c) hiding the Settings "danger zone" div. Any finer-grained, action-level button gating the module was designed to support (create vs. update vs. export, independent of module access) is not wired up anywhere. This means a `viewer` role (read+export only per `rbac.js:73-77`) sees the *same* Create/Edit/Delete-labelled buttons inside the Organisations/Awards/Entries tabs as an `editor` or `admin`, with no visual indication they're unauthorized, until the server rejects the actual write.

- **Confirmed (Medium): the delete-button-disabling logic no longer matches any real button.** `rbac.js:186-193` disables elements matching `.btn-outline-danger[onclick*="delete"], .btn-danger[onclick*="delete"]` for any role without the `delete` action. A check of the actual delete/archive buttons in `organisations.js` (lines 1025, 1711, 2059, 2107, 4168), `entries.js`, and `awards.js` found they all use the `data-action="moduleX.deleteY"` delegation pattern (e.g. `organisations.js:4168`: `data-action="orgsModule.deleteOrganisation"`) — **zero** `onclick="...delete..."` attributes exist anywhere in these files. The codebase evidently migrated to the `data-action` pattern project-wide at some point after this RBAC safeguard was written, and the safeguard was never updated to match. Practical effect: a `viewer` or `judge` role sees fully clickable, enabled "Archive"/delete buttons throughout the admin UI. Clicking one still fails server-side (`ROLE_PERMISSIONS` blocks the write for these roles), so no data-integrity risk exists, but the UI gives no advance warning and the intended defense-in-depth UI layer is effectively inert.

- **Confirmed (Low/Medium): GDPR UI access is gated by `'settings'` module access, not the `'gdpr'` action `rbac.js` otherwise models as a distinct, super_admin-only capability.** `rbac.js:27-38` lists `'gdpr'` as an action only `super_admin` has (`admin`'s action list at line 56 omits it). But `gdpr.js`'s `submitRequest()` (the only client-side gate on the GDPR panel) checks `rbacModule.canAccess('settings')`, not `rbacModule.canPerform('gdpr')` — and `'settings'` is a *module* both `admin` and `super_admin` can access (rbac.js:24, 53). Cross-checked against the server: `api/data-proxy.js:384-385` confirms `admin: { read: '*', write: '*' }`, identical to `super_admin`, for all generic table operations — so an `admin`-role user (not super_admin) can fully use GDPR export (which only performs generic table reads, no RPC) end-to-end today. Only the erasure/anonymisation paths are actually restricted to `super_admin`, via `ALLOWED_RPCS` (`api/data-proxy.js:91-93`) gating the two RPC calls specifically — this part does work as intended. **Net effect:** the "gdpr" action's apparent design intent (super_admin-exclusive) is only half-enforced; export is available to any `admin`, not just `super_admin`, with no code anywhere actually distinguishing the two roles for that specific capability.

### User/role administration — missing UI for an existing, tested backend

- **Confirmed (Medium-High, operational gap): a complete, tested, `super_admin`-gated user-management backend exists in `api/data-proxy.js` with no corresponding admin UI anywhere.** `tests/data-proxy-user-management.test.js`'s own docstring confirms five operations — `user_list`, `user_invite`, `user_set_role`, `user_set_status`, `user_reset_password` — are implemented and correctly gated to `super_admin`. A repository-wide grep for any frontend call to these operation names, or for `rbacModule`'s `manage_users` action (which exists in the permission model, rbac.js:34, and is checked once at rbac.js:196 only to hide the settings "danger zone" div) returned nothing beyond `rbac.js` itself. **There is currently no way to invite a user, change their role, disable their account, or trigger a password reset through the admin interface** — this would have to be done directly against Supabase (dashboard or SQL), outside the application entirely. This is a real, user-facing capability gap, not a security issue (the backend is correctly locked down) — just unreachable.

### Organisations, entries, awards, assignments, settings, marketing/sponsorship, areas/location

All six reviewed consistently: use `ModuleRegistry.register`, route every data operation through `apiClient` (never a direct Supabase call), use the `data-action`/`data-args` delegation pattern for click handling, and implement their own bulk-action toolbars independently (`organisations.js` bulk email at ~line 3125/3369; `entries.js` `bulkUpdateEntryStatus` at line 827, with its own activity-log entry per bulk change at line 866; `awards.js` `bulkSetStatus`/`bulkDelete` at lines 2182/2217, plus a `bulkApplySeasonDates` dropdown at line 2665). No two modules share a common bulk-action helper — each reimplements its own toolbar show/hide and confirm-dialog logic — a **Potential** (not confirmed defective, just unverified for subtle inconsistency) duplication-of-effort/maintenance-burden observation, not a functional defect found in this pass. Empty-state handling (`utils.showEmptyState`) is used in `organisations.js` and `awards.js` and `settings.js` but not observed in `entries.js`, `marketing.js`, or `dashboard.js` in this pass — **Unknown** whether those three have an equivalent empty-state pattern under a different name, or simply render nothing when a list is empty; not confirmed either way without a deeper per-module read than this task's time budget allowed.

No instance was found in this pass of an admin UI element invoking an API `action`/`operation` name that does not exist in `api/data-proxy.js` — i.e., no "button that calls an unimplemented API action" was confirmed. This was checked specifically for the modules named in this task's scope, not exhaustively for every button in a 28,000-line surface; absence of a finding here is **Unverified at full coverage**, not a clean bill of health claim.

## Prioritised issues list (not fixed, recorded only)

1. **Medium** — Update `rbac.js`'s delete-button-disable selector to match the current `data-action` pattern (or remove the dead selector and rely on the server-side gate alone, documenting that choice).
2. **Medium** — Decide and implement consistent action-level UI gating (wire up `data-rbac-action` where it matters, or formally drop that mechanism from `rbac.js` if module-level + server-side gating is considered sufficient).
3. **Medium** — Clarify whether GDPR *export* should actually be `super_admin`-only (matching the `'gdpr'` action's apparent intent) or deliberately available to any `admin` (matching what the code currently does) — this is a policy decision, not a pure bug.
4. **Medium-High** — Build an admin UI for the existing `user_list`/`user_invite`/`user_set_role`/`user_set_status`/`user_reset_password` operations, or explicitly document that user management is intentionally Supabase-dashboard-only.

## Scope note

This audit covered the modules and questions explicitly named in the task brief. It did not re-derive BTA-077's full role-permission cross-check (confirmed still consistent with what was checked here, no contradiction found) and did not attempt a line-by-line review of every admin screen given the surface's size (~28k lines across the files read). Deeper per-module UX review (loading states, accessibility, exact bulk-action parity) would need a dedicated follow-up if required.
